### Ⅱ. MVC와 MVVM

<BR>


# 2-1 MVC란?
→ Model, View, Controller로 역할을 나누는 아키텍처 패턴

### 1) Model
앱에서 사용하는 데이터와 관련 로직을 담당함

> ex - 사용자 정보, 게시글 데이터

### 2) View
사용자에게 화면을 보여주고 입력을 받음

> ex - 버튼, 텍스트, 목록 화면

### 3) Controller
사용자 입력을 처리하고 Model과 View를 연결함

iOS의 UIKit에서는 보통 `UIViewController`가 Controller 역할을 함


<BR>
<BR>


# 2-2 MVC의 데이터 흐름
1. 사용자가 View에서 버튼을 누름
2. Controller가 입력을 처리함
3. Controller가 Model을 조회하거나 변경함
4. Controller가 결과에 맞게 View를 갱신함

> 사용자 입력 → Controller → Model → Controller → View

<BR>
<BR>



# 2-3 MVC의 장단점과 주의점

### 장점
- 구조가 비교적 단순해서 이해하기 쉬움
- UIKit의 기본 구성과 잘 맞음
- 간단한 화면을 빠르게 만들기 좋음

### 주의점
- Controller에 화면 처리, 데이터 처리, 네트워크 요청 등이 몰릴 수 있음
- `UIViewController`가 너무 많은 역할을 맡아 비대해지는 문제를 **Massive View Controller**라고 부름


<BR>
<BR>


# 2-4 MVVM이란?
→ Model, View, ViewModel로 역할을 나누는 아키텍처 패턴

### 1) Model
앱에서 사용하는 데이터와 관련 로직을 담당함

### 2) View
화면을 표시하고 사용자 입력을 ViewModel에 전달함

### 3) ViewModel
View에 필요한 상태와 동작을 관리하고, Model의 데이터를 화면에 표시하기 좋은 형태로 준비함

> ViewModel은 화면에 표시할 데이터와 화면의 동작을 관리하지만, 화면 자체를 직접 그리지는 않음

<BR>
<BR>



# 2-5 MVVM의 데이터 흐름
1. 사용자가 View에서 동작을 수행함
2. View가 사용자 입력을 ViewModel에 전달함
3. ViewModel이 Model의 데이터를 조회하거나 변경함
4. ViewModel이 화면에 필요한 상태를 갱신함
5. View가 변경된 상태를 화면에 반영함

> 사용자 입력 → View → ViewModel → Model → ViewModel → View

<BR>
<BR>



# 2-6 UIKit과 SwiftUI에서의 MVVM

### UIKit
UIKit에서는 화면을 표시하는 `UIView`와 화면을 제어하는 `UIViewController`가 나뉘어 있음

MVVM을 적용하면 ViewController가 View 역할을 일부 맡고, 화면에 필요한 상태와 로직을 ViewModel로 분리할 수 있음

### SwiftUI
SwiftUI에서는 `View`가 화면을 선언적으로 표현하고, 상태가 바뀌면 화면이 다시 그려짐

SwiftUI의 `View`는 UIKit처럼 View와 ViewController로 나뉘지 않지만 그렇다고 View와 ViewModel이 하나가 되는 건 아님 MVVM을 적용하면 View는 화면과 사용자 입력을 담당하고 ViewModel은 화면 상태와 동작을 관리할 수 있음

> SwiftUI 자체가 MVVM인 것은 아니고
> SwiftUI는 UI를 만드는 프레임워크이고 MVVM은 코드를 나누는 아키텍처 패턴임


<BR>
<BR>


# 2-7 MVVM의 장단점과 주의점

### 장점
- View와 화면 상태·동작을 분리하기 좋음
- ViewModel을 별도로 테스트하기 쉬움
- 서버 통신 결과와 로딩·오류 상태를 화면 코드와 분리해 관리하기 굿

### 주의점
- 작은 기능에도 ViewModel을 많이 만들면 구조가 복잡해질 수 있음
- 요청, 데이터 가공, 화면 상태를 모두 ViewModel에 넣으면 ViewModel도 비대해질 수 있음
- View와 ViewModel 사이의 상태 전달 방식을 적절히 정해야 함


<BR>
<BR>


# 2-8 MVC와 MVVM 비교

| 구분 | MVC | MVVM |
|---|---|---|
| 구성 | Model, View, Controller | Model, View, ViewModel |
| 중간 역할 | Controller | ViewModel |
| 화면 상태 관리 | 주로 Controller | 주로 ViewModel |
| 화면 갱신 | Controller가 View를 갱신 | View가 ViewModel의 상태를 반영 |
| 주의할 점 | Controller가 커질 수 있음 | ViewModel이 커질 수 있음 |


<BR>
<BR>


# 2-9 정리
* MVC와 MVVM은 코드의 역할과 책임을 나누는 아키텍처 패턴
* MVC에서는 Controller가 Model과 View를 연결
* MVVM에서는 ViewModel이 화면에 필요한 상태와 동작을 관리
* UIKit은 보통 `UIViewController`를 중심으로 MVC를 구성
* SwiftUI는 MVVM을 강제하지 않지만, 상태 기반 UI라 MVVM과 함께 자주 사용함
