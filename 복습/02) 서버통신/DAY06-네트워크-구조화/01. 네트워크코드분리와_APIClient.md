### Ⅰ. 네트워크 코드 분리와 APIClient


<br>

# 1-1 네트워크 코드를 분리하는 이유

앱에서 화면을 구성하는 코드와 서버 통신 코드를 한곳에 모두 작성하면 코드가 복잡해짐

예를 들어 화면 코드가 URL 구성, 요청 전송, 응답 처리까지 직접 담당하면 다음 문제가 생길 수 있음

- 같은 네트워크 코드를 여러 화면에서 반복하게 됨
- 서버 주소나 요청 방식이 바뀌면 여러 곳을 수정해야 함
- 화면 코드가 길어져 기능을 파악하기 어려움
- 네트워크 오류를 한곳에서 일관되게 처리하기 어려움

그래서 서버 통신 코드를 별도 타입으로 분리해 관리할 수 있음


<br>
<br>



# 1-2 APIClient란?

→ 서버에 요청을 보내고 응답을 받는 네트워크 기능을 담당하는 타입

`APIClient`가 요청 전송을 맡으면 화면이나 뷰 모델은 필요한 데이터를 요청하고 결과를 처리하는 데 집중할 수 있음


> 화면 또는 뷰 모델 → APIClient에 요청 → 서버 통신 → 결과 전달


<br>
<br>



# 1-3 네트워크 코드가 한곳에 있을 때

화면 코드 안에서 직접 요청을 보내면 UI와 네트워크 처리가 섞임

```swift
func loadCharacter() {
    Task {
        guard let url = URL(string: "https://api.example.com/characters/1") else {
            return
        }

        do {
            let (data, _) = try await URLSession.shared.data(from: url)
            print(data)
        } catch {
            print(error)
        }
    }
}
```

요청이 간단할 때는 괜찮아 보여도 여러 화면에서 같은 방식을 사용하면 코드가 중복될 수 있음



<br>
<br>


# 1-4 APIClient로 요청 코드 분리하기

요청을 보내는 코드를 `APIClient`로 옮길 수 있음

```swift
import Foundation

final class APIClient {
    func fetchData(from url: URL) async throws -> Data {
        let (data, _) = try await URLSession.shared.data(from: url)
        return data
    }
}
```

이제 화면이나 뷰 모델은 `APIClient`에 데이터 요청을 맡길 수 있음

```swift
let client = APIClient()
let data = try await client.fetchData(from: url)
```

# 1-5 응답 상태 코드 확인하기

요청 코드를 분리할 때 HTTP 상태 코드 확인도 `APIClient`에서 처리할 수 있음

```swift
final class APIClient {
    func fetchData(from url: URL) async throws -> Data {
        let (data, response) = try await URLSession.shared.data(from: url)

        guard let httpResponse = response as? HTTPURLResponse else {
            throw URLError(.badServerResponse)
        }

        guard (200...299).contains(httpResponse.statusCode) else {
            throw URLError(.badServerResponse)
        }

        return data
    }
}
```

상태 코드가 성공 범위가 아니면 오류를 던지고 성공한 경우에만 응답 데이터를 반환함



<br>
<br>


# 1-6 APIClient에서 JSON 디코딩하기

> 응답 데이터를 모델로 변환하는 역할도 `APIClient`에 둘 수 있음

```swift
final class APIClient {
    func fetch<T: Decodable>(
        _ type: T.Type,
        from url: URL
    ) async throws -> T {
        let (data, response) = try await URLSession.shared.data(from: url)

        guard let httpResponse = response as? HTTPURLResponse,
              (200...299).contains(httpResponse.statusCode) else {
            throw URLError(.badServerResponse)
        }

        return try JSONDecoder().decode(T.self, from: data)
    }
}
```

`T: Decodable`은 전달한 타입이 JSON에서 디코딩될 수 있어야 한다는 뜻임

사용할 때는 응답 모델 타입을 지정함

```swift
let character = try await client.fetch(
    Character.self,
    from: url
)
```

# 1-7 화면과 APIClient의 역할 나누기

각 역할을 나누면 코드의 목적을 파악하기 쉬워짐

### 1) APIClient

- 요청 전송
- 응답 상태 확인
- JSON 디코딩
- 네트워크 오류 전달

### 2) 화면 또는 뷰 모델

- 데이터를 요청할 시점 결정
- 요청 결과를 화면 상태에 반영
- 로딩이나 오류 화면 표시


<br>
<br>



# 1-8 사용 예시

```swift
struct Character: Decodable {
    let id: Int
    let name: String
}

let client = APIClient()

func loadCharacter() async {
    guard let url = URL(string: "https://api.example.com/characters/1") else {
        return
    }

    do {
        let character = try await client.fetch(
            Character.self,
            from: url
        )
        print(character.name)
    } catch {
        print("캐릭터 정보를 불러오지 못했어요 :", error)
    }
}
```

뷰 모델이나 화면은 `URLSession`을 직접 다루지 않고 <mark>`APIClient`를 통해 데이터를 요청함

<br>




# 1-9 네트워크 코드를 분리할 때 주의할 점

- `APIClient`가 너무 많은 역할을 맡지 않도록 책임을 나누는 것이 좋음
- 서버 주소와 요청 경로는 API 문서를 기준으로 설정해야 함
- 요청 실패와 HTTP 상태 코드 오류를 구분해 처리해야 함
- 실제 응답 JSON 구조와 모델의 키·자료형이 맞는지 확인해야 함
- 구조와 이름은 프로젝트 규모나 설계 방식에 따라 달라질 수 있음

# 1-10 정리

* 네트워크 코드를 화면 코드와 분리하면 중복과 복잡도를 줄일 수 있음
* `APIClient`는 요청 전송과 응답 처리를 담당하는 타입
* 상태 코드 확인과 JSON 디코딩을 APIClient에 모아둘 수 있음
* 화면이나 뷰 모델은 데이터 요청과 화면 상태 관리에 집중할 수 있음
* 역할을 나누면 코드 수정과 테스트가 쉬워짐

<br>

> ### ⇒ 네트워크 처리를 `APIClient`에 모아두면 화면 코드는 결과를 사용하는 데 집중할 수 있음 ✨
