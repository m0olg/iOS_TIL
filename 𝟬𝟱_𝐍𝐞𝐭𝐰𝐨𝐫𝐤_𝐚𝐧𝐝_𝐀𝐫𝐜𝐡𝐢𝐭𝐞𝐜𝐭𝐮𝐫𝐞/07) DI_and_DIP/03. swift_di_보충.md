# DI

<br>


# 01 `DI`란?

→ `DI`는 `Dependency Injection`의 약자로, **클래스가 내부에서 직접 생성하던 객체를 외부에서 생성한 뒤 전달받는 설계 방식**

즉, 클래스가 필요한 객체를 직접 만들지 않고 외부에 맡기는 것

```swift
class Player {
    let agent: Agent

    init(agent: Agent) {
        self.agent = agent
    }
}
```

`Player`는 `Agent`를 직접 생성하지 않고 외부에서 전달받음


<br>
<br>



# 02 의존성이란?

클래스 A가 클래스 B의 기능이나 객체를 사용하고 있을 때, 클래스 A는 클래스 B에 **의존성을 갖는다**고 말함

예를 들어 `Player`가 `Agent`를 사용한다면 `Player`는 `Agent`에 의존하고 있음

```swift
class Agent {
    let name: String

    init(name: String) {
        self.name = name
    }
}

class Player {
    let agent: Agent

    init() {
        self.agent = Agent(name: "클로브")
    }
}
```

```swift
let player = Player()

print(player.agent.name) // 클로브
```

이 코드에서 `Player`는 `Agent`에 의존하고 있음

왜냐하면 `Player` 내부에서 직접 `Agent` 객체를 생성하고 있기 때문임

```swift
self.agent = Agent(name: "클로브")
```

`Player`는 다음과 같은 내용을 알고 있음

* 사용해야 할 클래스가 `Agent`라는 것
* `Agent`를 생성하는 방법
* 생성할 때 `"클로브"`라는 이름을 전달해야 하는 것

이처럼 한 클래스가 다른 클래스의 구체적인 생성 방식까지 알고 있으면 두 클래스의 결합도가 높다고 말함


<br>
<br>



# 03 결합도란?

결합도는 클래스나 객체가 서로 얼마나 강하게 연결되어 있는지를 의미함

`Player`가 `Agent`를 직접 생성하는 경우 두 클래스의 결합도가 높음

```swift
class Player {
    let agent: Agent

    init() {
        self.agent = Agent(name: "클로브")
    }
}
```

이 코드에서는 `Agent`의 생성 방식이 바뀌면 `Player`도 수정해야 함

예를 들어 `Agent`의 이니셜라이저가 다음과 같이 변경되었다고 해보자

```swift
class Agent {
    let name: String
    let role: String

    init(name: String, role: String) {
        self.name = name
        self.role = role
    }
}
```

그러면 `Player`도 함께 수정해야 함

```swift
class Player {
    let agent: Agent

    init() {
        self.agent = Agent(
            name: "클로브",
            role: "컨트롤러"
        )
    }
}
```

이처럼 한 클래스의 변경이 다른 클래스의 변경으로 이어지면 두 클래스가 강하게 결합되어 있다고 볼 수 있음



<br>
<br>


# 04 주입이란?

→ `Injection`은 필요한 객체를 외부에서 전달하는 것을 의미함

DI에서는 보통 다음 3가지 방식으로 의존성을 주입할 수 있음

1. 이니셜라이저 주입
2. 프로퍼티 주입
3. 메서드 주입




## 4-1 이니셜라이저 주입

객체를 생성할 때 필요한 의존성을 이니셜라이저의 매개변수로 전달하는 방식

```swift
class Agent {
    let name: String

    init(name: String) {
        self.name = name
    }
}

class Player {
    let agent: Agent

    init(agent: Agent) {
        self.agent = agent
    }
}
```

```swift
let agent = Agent(name: "클로브")
let player = Player(agent: agent)
```

`Player`는 `Agent`를 직접 생성하지 않고 외부에서 전달받음

### 🍀 장점

1. 필요한 의존성이 무엇인지 명확함
2. 객체가 생성될 때부터 완전한 상태를 가짐
3. `let`으로 선언할 수 있어 안정적임
4. 의존성이 누락된 객체를 만들기 어려움
5. 테스트하기 쉬움

```swift
let testAgent = Agent(name: "테스트 에이전트")
let testPlayer = Player(agent: testAgent)
```

> 반드시 필요한 의존성이라면 이니셜라이저 주입을 사용하는 것이 가장 적합함


<br>
<br>

## 4-2 프로퍼티 주입

객체를 먼저 생성한 후 프로퍼티에 의존성을 전달하는 방식

```swift
class Player {
    var agent: Agent?

    init() {}
}
```

```swift
let player = Player()

player.agent = Agent(name: "제트")
```

### 🍀 장점

1. 의존성을 나중에 주입할 수 있음
2. 의존성이 선택적인 경우 사용할 수 있음
3. 객체 생성과 의존성 설정을 분리할 수 있음

### 😈 단점

1. 의존성이 주입되지 않은 상태로 객체가 만들어질 수 있음
2. 옵셔널을 사용해야 하는 경우가 많음
3. 언제 의존성이 주입되는지 추적하기 어려움
4. 의존성이 없는 상태에서 메서드가 실행될 수 있음

> 반드시 필요한 의존성이라면 프로퍼티 주입보다 이니셜라이저 주입이 적합함

<br>
<br>


## 4-3 메서드 주입

특정 메서드를 호출할 때 의존성을 전달하는 방식

```swift
class PongPingManager {
    func startPongPing(with agent: Agent) {
        print("\(agent.name) 레이즈의 폭탄 파티쇼 시작")
    }
}
```

```swift
let manager = PongPingManager()
let agent = Agent(name: "레이즈")

manager.startPongPing(with: agent)
```

이 방식은 의존성이 특정 기능을 실행할 때만 필요한 경우에 적합함

예를 들어 `PongPingManager`가 항상 `Agent`를 필요로 하는 것이 아니라 `startPongPing`을 실행할 때만 필요하다면 메서드 주입을 사용할 수 있음


<br>
<br>



# 05 의존성 분리

의존성 분리란 클래스가 특정 구현체에 직접 의존하지 않고 추상화에 의존하도록 만드는 것임

여기서 추상화는 보통 프로토콜을 의미함

```swift
protocol AgentType {
    var name: String { get }
}
```

`Player`가 `Agent`가 아닌 `AgentType`을 받도록 변경함

```swift
class Player {
    let agent: AgentType

    init(agent: AgentType) {
        self.agent = agent
    }
}
```

이제 `Player`는 `Agent`라는 특정 클래스가 아니라 `AgentType`을 채택한 객체라면 모두 사용할 수 있음

```swift
class Agent: AgentType {
    let name: String

    init(name: String) {
        self.name = name
    }
}
```

```swift
class MockAgent: AgentType {
    let name = "테스트 에이전트"
}
```

```swift
let agent = Agent(name: "클로브")
let mockAgent = MockAgent()

let player1 = Player(agent: agent)
let player2 = Player(agent: mockAgent)
```

`Player`를 수정하지 않고도 다른 에이전트를 사용할 수 있음

### 핵심 ⭐⭐⭐

* 에이전트 교체가 쉬워짐
* 테스트용 객체를 넣기 쉬워짐
* 클래스 간 결합도가 낮아짐
* 다른 클래스의 변경이 `Player`에 미치는 영향이 줄어듦



<br>
<br>


# 06 프로토콜과 의존성 분리

`Player`가 특정 클래스인 `Agent`가 아니라 프로토콜인 `AgentType`에 의존하도록 만드는 것이 의존성 분리임

```swift
protocol AgentType {
    var name: String { get }
    func useSkill()
}
```

`Agent`가 프로토콜을 채택함

```swift
class Agent: AgentType {
    let name: String

    init(name: String) {
        self.name = name
    }

    func useSkill() {
        print("\(name)이 스킬을 사용합니다.")
    }
}
```

`Player`는 `Agent`가 아닌 `AgentType`을 받음

```swift
class Player {
    let agent: AgentType

    init(agent: AgentType) {
        self.agent = agent
    }

    func play() {
        print("\(agent.name)을 사용합니다.")
        agent.useSkill()
    }
}
```

이제 `Player`는 특정 에이전트 클래스에 묶이지 않음

`AgentType`을 채택한 객체라면 모두 사용할 수 있음

```swift
let agent = Agent(name: "클로브")
let player = Player(agent: agent)

player.play()
```

# 07 `DI`와 `DIP`의 관계

`DI`와 `DIP`는 비슷해 보이지만 <mark>서로 다른 개념</mark>임

| 개념 | 의미 |
| :--- | :--- |
| **DI** | 의존성을 외부에서 주입하는 방법 |
| **DIP** | 구체적인 구현체보다 추상화에 의존해야 한다는 원칙 |

예를 들어 다음 코드는 DI를 사용하고 있음

```swift
class Player {
    let agent: Agent

    init(agent: Agent) {
        self.agent = agent
    }
}
```

`Agent`를 외부에서 주입받고 있으므로 DI는 적용됨

하지만 `Player`가 여전히 구체적인 클래스인 `Agent`에 의존하고 있음

```swift
let player = Player(
    agent: Agent(name: "클로브")
)
```

프로토콜을 사용하면 DIP까지 적용할 수 있음

```swift
protocol AgentType {
    var name: String { get }
}
```

```swift
class Player {
    let agent: AgentType

    init(agent: AgentType) {
        self.agent = agent
    }
}
```

이제 `Player`는 구체적인 `Agent`가 아니라 추상화인 `AgentType`에 의존함

> DI는 DIP를 구현하기 위해 사용할 수 있는 대표적인 방법임


<br>
<br>



# 08 `IoC`란?

`IoC`는 `Inversion of Control`의 약자로, 한국어로 **제어의 역전**을 의미함

일반적인 구조에서는 클래스가 필요한 객체를 직접 생성함

```swift
class Player {
    let agent: Agent

    init() {
        self.agent = Agent(name: "클로브")
    }
}
```

이 경우 객체 생성의 제어권이 `Player`에게 있음

`Player`가 직접 `Agent`를 만들고 있기 때문임

반면 IoC 구조에서는 외부에서 객체를 만들고 연결함

```swift
let agent = Agent(name: "클로브")
let player = Player(agent: agent)
```

이제 `Player`는 `Agent`를 직접 생성하지 않음

객체 생성과 연결의 책임이 `Player` 외부로 이동함

> IoC는 객체 생성과 제어의 책임을 외부로 넘기는 더 큰 개념이고, DI는 이를 구현하는 방법 중 하나임


<br>
<br>



# 09 `IoC Container`란?

`IoC Container`는 객체를 생성하고 서로 연결하는 역할을 담당하는 객체임

객체가 많아지면 의존성을 생성하고 주입하는 코드가 여러 곳에 흩어질 수 있음

이때 앱에서 사용할 객체를 한 곳에서 관리할 수 있음

```swift
class AppContainer {
    let agent: Agent
    let player: Player

    init() {
        self.agent = Agent(name: "클로브")
        self.player = Player(agent: agent)
    }
}
```

```swift
let container = AppContainer()

let player = container.player
print(player.agent.name)
```

`AppContainer`가 다음 작업을 담당함

* `Agent` 객체 생성
* `Player` 객체 생성
* `Agent`를 `Player`에 주입
* 객체 간 연결 관리

즉, `AppContainer`는 객체 생성과 연결을 담당하는 IoC Container임


<br>

# 10 SwiftUI에서 DI가 필요한 이유

SwiftUI에서는 <mark>DI가 특히 **프리뷰를 실행하기 위해서** 많이 사용</mark>됨

SwiftUI 프리뷰는 앱 전체를 실행하는 것이 아니라 특정 뷰를 빠르게 보여주는 기능임

그런데 뷰가 생성될 때 다음과 같은 작업이 실행되면 프리뷰가 작동하지 않을 수 있음

* 네트워크 요청
* 데이터베이스 연결
* Firebase와 같은 외부 SDK 초기화
* 로그인 상태 확인
* 파일 접근
* 실제 서버와 통신하는 작업

예를 들어 다음과 같은 뷰가 있다고 해보자

```swift
struct UserView: View {
    @StateObject private var viewModel = UserViewModel()

    var body: some View {
        Text(viewModel.userName)
    }
}
```

그리고 `UserViewModel`이 내부에서 `UserService`를 직접 생성하고 있다면

```swift
class UserViewModel: ObservableObject {
    @Published var userName = ""

    private let service = UserService()

    init() {
        service.fetchUser()
    }
}
```

`UserViewModel`이 생성될 때 `UserService`도 함께 생성됨

이때 `UserService`가 네트워크 요청을 보내거나 외부 SDK를 초기화하면 프리뷰에서도 해당 코드가 실행됨

따라서 다음과 같은 문제가 발생할 수 있음

* 프리뷰가 느려짐
* 네트워크가 연결되지 않으면 오류가 발생함
* 외부 SDK 초기화에 실패할 수 있음
* 테스트할 때 실제 서버에 요청하게 됨
* 화면만 확인하고 싶은데 불필요한 작업까지 실행됨

이 문제를 해결하려면 `UserViewModel`이 `UserService`를 직접 생성하지 않고 외부에서 전달받도록 변경해야 함

<br>
<br>




# 11 프로토콜을 활용한 SwiftUI DI

먼저 서비스가 제공해야 하는 기능을 프로토콜로 정의함

```swift
protocol UserServiceType {
    func fetchUserName() async throws -> String
}
```

실제 앱에서 사용할 서비스 구현

```swift
class UserService: UserServiceType {
    func fetchUserName() async throws -> String {
        // 실제 네트워크 통신
        return "실제 사용자"
    }
}
```

프리뷰와 테스트에서 사용할 Mock 구현

```swift
class MockUserService: UserServiceType {
    func fetchUserName() async throws -> String {
        return "프리뷰 사용자"
    }
}
```

이제 `UserViewModel`이 `UserService`가 아니라 `UserServiceType`을 받도록 수정함

```swift
class UserViewModel: ObservableObject {
    @Published var userName = ""

    private let service: UserServiceType

    init(service: UserServiceType) {
        self.service = service
    }

    func loadUser() async {
        do {
            userName = try await service.fetchUserName()
        } catch {
            userName = "사용자 정보를 불러오지 못했습니다."
        }
    }
}
```

이제 `UserViewModel`은 어떤 서비스가 들어오는지 직접 알 필요가 없음

`UserService`가 들어올 수도 있고 `MockUserService`가 들어올 수도 있음

중요한 것은 두 객체 모두 `UserServiceType`에 정의된 기능을 제공한다는 점임


<br>
<br>



# 12 SwiftUI View에 DI 적용하기

`UserViewModel`에 서비스를 주입받도록 만들었으므로 `UserView`에서도 서비스를 외부에서 전달받아야 함

```swift
struct UserView: View {
    @StateObject private var viewModel: UserViewModel

    init(service: UserServiceType) {
        _viewModel = StateObject(
            wrappedValue: UserViewModel(service: service)
        )
    }

    var body: some View {
        Text(viewModel.userName)
            .task {
                await viewModel.loadUser()
            }
    }
}
```

실제 앱에서는 실제 서비스를 주입함

```swift
UserView(service: UserService())
```

프리뷰에서는 Mock 서비스를 주입함

```swift
#Preview {
    UserView(service: MockUserService())
}
```

이렇게 하면 프리뷰에서는 실제 네트워크 요청을 보내지 않고 `"프리뷰 사용자"`라는 값을 사용하게 됨

즉, 프리뷰에서 실제 객체 대신 가짜 객체를 주입하는 것임



<br>

# 13 `Mock` 객체란?

`Mock`은 테스트나 프리뷰를 위해 만든 가짜 객체임

실제 객체와 같은 기능을 제공하지만 실제 네트워크나 데이터베이스에는 접근하지 않음

```swift
class MockUserService: UserServiceType {
    func fetchUserName() async throws -> String {
        return "프리뷰 사용자"
    }
}
```

위 코드의 `MockUserService`는 실제 서버에 요청하지 않고 미리 정해진 문자열만 반환함

따라서 다음과 같은 상황에서도 사용할 수 있음

* 네트워크가 연결되지 않은 경우
* 서버가 아직 완성되지 않은 경우
* 특정 데이터를 반복해서 확인하고 싶은 경우
* 오류 화면을 만들고 싶은 경우
* SwiftUI 프리뷰를 실행하고 싶은 경우
* 실제 서버에 요청하지 않고 테스트하고 싶은 경우

# 14 상태별 `Mock` 만들기

성공한 경우만 확인하는 것이 아니라 빈 화면이나 오류 화면도 확인해야 함

이때 Mock 객체가 상황에 따라 다른 결과를 반환하도록 만들 수 있음

```swift
enum MockUserState {
    case success
    case empty
    case failure
}
```

```swift
class MockUserService: UserServiceType {
    private let state: MockUserState

    init(state: MockUserState) {
        self.state = state
    }

    func fetchUserName() async throws -> String {
        switch state {
        case .success:
            return "프리뷰 사용자"

        case .empty:
            return ""

        case .failure:
            throw URLError(.badServerResponse)
        }
    }
}
```

상태별로 다른 프리뷰를 만들 수 있음

```swift
#Preview("성공") {
    UserView(
        service: MockUserService(state: .success)
    )
}
```

```swift
#Preview("빈 화면") {
    UserView(
        service: MockUserService(state: .empty)
    )
}
```

```swift
#Preview("실패") {
    UserView(
        service: MockUserService(state: .failure)
    )
}
```

이렇게 하면 실제 서버의 상태를 기다리지 않고도 다양한 화면을 확인할 수 있음

# 15 DI와 테스트

DI를 사용하면 테스트용 객체를 외부에서 주입할 수 있기 때문에 테스트하기 쉬워짐

DI를 사용하지 않는 경우

```swift
class CalculatorViewModel {
    private let calculator = RealCalculator()
}
```

위 코드에서는 `CalculatorViewModel`이 항상 `RealCalculator`를 사용함

따라서 테스트할 때도 실제 계산기를 사용해야 함

DI를 적용하면 다음과 같이 변경할 수 있음

```swift
protocol CalculatorType {
    func add(_ a: Int, _ b: Int) -> Int
}
```

```swift
class CalculatorViewModel {
    private let calculator: CalculatorType

    init(calculator: CalculatorType) {
        self.calculator = calculator
    }
}
```

테스트용 계산기를 만들 수 있음

```swift
class MockCalculator: CalculatorType {
    func add(_ a: Int, _ b: Int) -> Int {
        return 999
    }
}
```

```swift
let viewModel = CalculatorViewModel(
    calculator: MockCalculator()
)
```

이제 테스트에서는 실제 계산기 대신 `MockCalculator`를 주입할 수 있음

# 16 `@Environment`를 활용한 DI

SwiftUI에서는 생성자의 매개변수로 의존성을 전달하는 방법 외에도 `@Environment`를 사용할 수 있음

`@Environment`를 사용하면 여러 하위 뷰에 공통으로 사용하는 객체를 전달할 수 있음

먼저 `EnvironmentKey`를 정의함

```swift
private struct UserServiceKey: EnvironmentKey {
    static let defaultValue: UserServiceType = MockUserService()
}
```

그 다음 `EnvironmentValues`에 프로퍼티를 추가함

```swift
extension EnvironmentValues {
    var userService: UserServiceType {
        get {
            self[UserServiceKey.self]
        }
        set {
            self[UserServiceKey.self] = newValue
        }
    }
}
```

뷰에서는 다음과 같이 사용함

```swift
struct UserView: View {
    @Environment(\.userService)
    private var userService

    var body: some View {
        Text("사용자 화면")
    }
}
```

프리뷰에서는 Mock 서비스를 주입할 수 있음

```swift
#Preview {
    UserView()
        .environment(
            \.userService,
            MockUserService()
        )
}
```

실제 앱에서는 실제 서비스를 주입함

```swift
@main
struct MyApp: App {
    var body: some Scene {
        WindowGroup {
            UserView()
                .environment(
                    \.userService,
                    UserService()
                )
        }
    }
}
```

### 생성자 주입과 `@Environment` 비교

| 방식 | 설명 |
| :--- | :--- |
| 생성자 주입 | 필요한 의존성을 직접 전달하는 방식 |
| `@Environment` | 여러 하위 뷰에 공통 의존성을 전달하는 방식 |
| 생성자 주입 | 어떤 의존성이 필요한지 명확하게 알 수 있음 |
| `@Environment` | 여러 뷰에 같은 의존성을 전달하기 편함 |
| 생성자 주입 | 반드시 필요한 의존성에 적합 |
| `@Environment` | 앱 전역 설정이나 공통 서비스에 적합 |

따라서 반드시 필요한 의존성은 생성자 주입을 사용하는 것이 좋고 여러 화면에서 공통으로 사용하는 의존성은 `@Environment`를 사용할 수 있음

# 17 `@EnvironmentObject`를 활용한 DI

SwiftUI에서는 `@EnvironmentObject`를 사용해서 공통으로 사용하는 객체를 전달할 수도 있음

먼저 공유할 객체를 만듦

```swift
class AppState: ObservableObject {
    @Published var isLoggedIn = false
}
```

상위 뷰에서 객체를 주입함

```swift
@main
struct MyApp: App {
    @StateObject private var appState = AppState()

    var body: some Scene {
        WindowGroup {
            ContentView()
                .environmentObject(appState)
        }
    }
}
```

하위 뷰에서는 `@EnvironmentObject`로 가져옴

```swift
struct ContentView: View {
    @EnvironmentObject
    private var appState: AppState

    var body: some View {
        Text(
            appState.isLoggedIn
            ? "로그인됨"
            : "로그아웃됨"
        )
    }
}
```

`@EnvironmentObject`를 사용하면 여러 뷰에서 같은 객체를 공유할 수 있음

하지만 객체가 어디에서 주입되는지 코드만 보고 바로 알기 어렵다는 단점이 있음

또한 객체를 주입하지 않고 뷰를 실행하면 런타임 오류가 발생할 수 있음

따라서 다음처럼 사용하는 것이 좋음

* 반드시 필요한 의존성 → 생성자 주입
* 여러 하위 뷰가 공유하는 상태 → `@EnvironmentObject`
* 환경에 따라 바뀌는 서비스 → `@Environment`

# 18 DI를 적용하는 순서

#### DI를 적용할 때는 다음 순서로 진행하면 됨
1. 클래스 내부에서 직접 생성하는 객체를 찾음
2. 해당 객체가 제공해야 하는 기능을 프로토콜로 정의함
3. 실제 앱에서 사용할 구현체를 만듦
4. 테스트와 프리뷰에서 사용할 Mock 구현체를 만듦
5. 클래스의 이니셜라이저에서 프로토콜 타입을 받도록 변경함
6. 실제 앱에서는 실제 구현체를 주입함
7. 프리뷰와 테스트에서는 Mock 구현체를 주입함

기존 코드가 다음과 같다면

```swift
class UserViewModel {
    private let service = UserService()
}
```

다음처럼 변경함

```swift
protocol UserServiceType {
    func fetchUserName() async throws -> String
}
```

```swift
class UserViewModel {
    private let service: UserServiceType

    init(service: UserServiceType) {
        self.service = service
    }
}
```

이제 `UserViewModel`은 `UserService`를 직접 생성하지 않음

따라서 실제 앱에서는 `UserService`를 주입하고 프리뷰에서는 `MockUserService`를 주입할 수 있음

# 19 DI를 사용할 때 주의할 점

DI가 항상 필요한 것은 아님

모든 객체를 프로토콜로 만들고 외부에서 주입하면 코드가 오히려 복잡해질 수 있음

### DI를 사용하면 좋은 경우 🍀
* 네트워크 서비스
* 데이터베이스
* 파일 저장소
* 로그인과 인증 관리 객체
* 외부 SDK
* 결제 기능
* 앱 전역 상태
* 프리뷰에서 다른 객체로 교체해야 하는 경우
* 테스트에서 가짜 객체를 사용해야 하는 경우

### DI가 없어도 되는 경우 ‼️

```swift
struct User {
    let name: String
}
```

> 위와 같은 단순한 값 타입까지 DI를 적용할 필요는 없음

또한 모든 클래스에 무조건 프로토콜을 만들 필요도 없음

다음과 같은 경우에 프로토콜을 사용하는 것이 좋음

* 테스트할 때 다른 구현체로 교체해야 하는 경우
* 여러 구현체가 존재하는 경우
* 네트워크나 데이터베이스처럼 외부 시스템과 통신하는 경우
* 나중에 변경될 가능성이 큰 경우

# 20 DI, IoC, DIP의 관계

| 개념 | 의미 |
| :--- | :---: |
| **DI** | 필요한 의존성을 외부에서 주입하는 방법 |
| **IoC** | 객체 생성과 제어의 책임을 외부로 넘기는 개념 |
| **IoC Container** | 객체 생성과 연결을 관리하는 객체 |
| **DIP** | 구체적인 구현보다 추상화에 의존해야 한다는 설계 원칙 |
| **Mock** | 테스트와 프리뷰를 위한 가짜 구현체 |

각 개념의 관계는 다음과 같음

* DIP를 지키기 위해 프로토콜을 사용함
* 프로토콜을 채택한 구현체를 DI로 주입함
* 여러 객체의 생성과 연결을 IoC Container에서 관리할 수 있음
* 테스트와 프리뷰에서는 실제 구현체 대신 Mock 객체를 주입함






# 21 최종 정리

* DI는 필요한 객체를 클래스 내부에서 직접 생성하지 않고 외부에서 주입받는 방식
* 의존성은 한 객체가 다른 객체의 기능이나 객체에 의존하는 관계
* 결합도가 높으면 한 클래스의 변경이 다른 클래스의 변경으로 이어질 수 있음
* 가장 기본적이고 권장되는 DI 방식은 이니셜라이저 주입
* 프로퍼티 주입은 의존성이 나중에 들어오거나 선택적인 경우에 사용
* 메서드 주입은 특정 기능을 실행할 때만 의존성이 필요한 경우에 사용
* 프로토콜에 의존하면 구체적인 구현체를 쉽게 교체할 수 있음
* IoC는 객체 생성과 제어의 책임을 외부로 넘기는 개념
* IoC Container는 객체를 생성하고 연결하는 역할을 담당
* DIP는 구체적인 클래스보다 추상화에 의존하라는 원칙
* Mock 객체를 사용하면 프리뷰와 테스트에서 실제 네트워크나 데이터베이스를 사용하지 않아도 됨
* SwiftUI 프리뷰에서는 실제 서비스 대신 Mock 서비스를 주입하는 것이 좋음
* 반드시 필요한 의존성은 생성자 주입을 사용하는 것이 가장 안전함


> ⇒ DI는 클래스가 필요한 객체를 직접 만들지 않고 외부에서 전달받도록 하여 코드의 결합도를 낮추고 테스트와 SwiftUI 프리뷰를 쉽게 만드는 설계 방식 ✨
